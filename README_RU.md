# Промты BIMCraft

[English](README.md) | **Русский**

Эта папка хранит **промты (спецификации) для BIMCraft** — готовые, самодостаточные файлы задач, которые скармливаются харнессу с нейросетью (OpenCode, Claude Code или любому другому ИИ-харнессу для программирования). Харнесс читает спецификацию и выдаёт **новый функционал в проект [BIMCraft](https://github.com/IPedrax/BIMCraft)**: модель реализует задачу, и вы получаете рабочий код, а не диалог.

Каждый файл — это не короткая просьба вида «почини стыки», а полная рабочая спецификация: в ней описано текущее поведение, указаны конкретные места в коде, которые вызывают проблему, сформулировано требуемое поведение в виде проверяемых требований, намечен технический план, перечислены подводные камни и определены тесты, которые должны подтвердить результат. Именно это делает один файл достаточным входом для харнесса — модели не приходится додумывать контекст.

## Зачем нужен этот репозиторий

- **Спецификация внутрь — фича наружу.** Один файл уходит в харнесс, реализованный функционал выходит из него. Задачу не нужно объяснять модели в чате — всё, что модели нужно знать, уже лежит в файле.
- **Повторяемые запуски.** Одну и ту же спецификацию можно скармливать харнессу снова — в новой сессии, на более новой модели или после неудачной попытки — вход остаётся идентичным.
- **История и ревью.** Спецификации хранятся в git рядом с порождённым ими кодом — всегда видно, что просили, почему и какие были границы scope.

## Именование файлов

```
SPEC-<NNN>-<короткий-заголовок-в-kebab-case>.md
```

Пример:

- `SPEC-007-strip-foundation-handles-joints-bonding.md`

`NNN` — порядковый номер, который сохраняет порядок спецификаций и позволяет ссылаться друг на друга (`Related specs: SPEC-006-…`).

## Структура спецификации

Каждая спецификация следует одной и той же схеме:

| Раздел | На какой вопрос отвечает |
| --- | --- |
| Заголовок | Статус (`specification, not implemented`), дата, ссылка на проект/сборка, связанные спецификации, тип задачи, при необходимости — скриншот дефекта |
| 1. Контекст и задача | В чём фича, что сейчас не так, подтверждённые пользователем решения по scope |
| 2. Почему сейчас так устроено (причины) | Первоисточники проблемы в текущем коде, по файлам — чтобы агент стартовал из фактов, а не из догадок |
| 3. Термины | Глоссарий проектной лексики (run, mitre, grip, glue, …) |
| 4. Функциональные требования | Нумерованные проверяемые требования, которые должна удовлетворить реализация |
| 5. Технический план | Куда именно вносить изменения (модули, команды, формат данных), без написания кода |
| 6. Подводные камни | Известные ловушки, которые нельзя сломать (регрессии, допуски, производительность, формат файла, локализация) |
| 7. Тесты | Конкретные сценарии тестов, доказывающие выполнение требований |
| Последующие разделы | Ограничения/out-of-scope и всё специфичное для задачи |

## Как использовать спецификацию

1. Выберите файл с фичей, которую хотите получить.
2. Запустите сессию харнесса в рабочей копии BIMCraft (в заголовке спецификации указаны рабочая копия, ветка и версия формата проекта, для которых она писалась).
3. Скармьте файл спецификации харнессу как вход задачи — например, дайте путь к файлу и попросите реализовать то, что в нём указано. Модель читает файл, следует его требованиям, техническому плану и подводным камням и пишет код в проект.
4. Когда харнесс закончит, проверьте результат по списку тестов из раздела 7 спецификации.
5. Если в спецификации упомянуты связанные спецификации — скармите и их харнессу: они описывают соседнее поведение, которого нельзя сломать.
6. Обновите `Status:` в заголовке спецификации, когда код смержен.

## Как добавить новую спецификацию

1. Возьмите следующий свободный номер и создайте `SPEC-<NNN>-<title>.md`.
2. Заполните заголовок: статус, дата, ссылка на проект, связанные спецификации, тип задачи.
3. Сохраняйте структуру выше. Раздел *Почему сейчас так устроено (причины)* обязателен — спецификация без локализованных первопричин это лишь пожелание, а не промт.
4. Явно указывайте решения по scope (что входит в задачу, что вне её).
5. Заканчивайте тестами, по которым ревьюер сможет убедиться, что задача выполнена.
6. Обновляйте `Status:` в заголовке, когда спецификация реализована.

## Соглашения

- Спецификации пишутся на **английском** (файл `README.md` — на английском; `README_RU.md` — русская версия этого readme).
- Статус — один из: `specification, not implemented`, `in progress`, `implemented`.
- Требования формулируются нумерованными проверяемыми утверждениями; каждый тест ссылается обратно на требования.
- Всё специфичное для проекта (пути к файлам, команды, форматы) должно быть конкретным — расплывчатые ссылки убивают смысл файла.
